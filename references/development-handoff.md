# 实现、排障与交付

## 本地开发

先核对真实目标模块、现有同类实现、构建与依赖。只有用户明确授权实施才写代码；已有项目做最小差异，不初始化另一套工程、不重构无关模块、不新增无必要开关和兼容层。

- E9：动态 SQL 标识符须有白名单/真实元数据约束，值参数绑定；Action 返回语义、节点时机、事务和现场 SDK 不能凭记忆推断。前端保留初始数据、增删改事件与非目标隔离，不能用 DOM 操作替代已确认的字段 API。
- E10：版本未知可分析，不生成未经确认的平台调用；数据写入只用现场确认的 API/RPC。不得用猜测的 JDBC/MyBatis、Hook 或内部 URL 绕过证据不足。标准业务 API、低代码和平台查询能力按已核验证据选择，不默认直接 SQL。
- 前端只控制体验，不能代替后端身份、数据权限和审计。新增复杂逻辑解释原因，延续项目异常和脱敏日志风格。

## 排障与验证

诊断请求先找实际配置、调用链、输入输出和失败证据，不擅自修复。外部请求超时可能已经生效，先核对目标状态和幂等依据，不自动重放。

按本次风险选择最小验证：缺陷复现、正常/空值/失败/重复/权限边界、受影响模块测试和编译。没有框架或依赖时说明缺口，可给具体手工检查；不为了“验证通过”引入未获准的新依赖。

分别记录静态、编译、单元或模拟、宿主加载、平台导入、客户业务与非目标回归。某层通过不能替另一层背书。只报实际命令与结果，不把计划执行写成已执行。

专项安全/性能审核只在用户请求或当前风险确有需要时加载已接入模块。保留原 JSON 契约，中文摘要另写；综合结论同时看 `decision`、`riskState`、`assuranceLevel` 和待核验项，不能只凭 `PASS` 认定无风险。摘要变化后的旧审核不能当作新制品审批。

## 项目人员能用的交付

面向首次接手的项目人员，优先把一次最小演练放在前面：必要文件/配置、操作命令和可观察结果就近给出，详细参数及排障后置；不要让其先读测试源码或完整维护记录。核验数量时写明记录数、文件数等具体对象；需要查看退出状态时再给对应终端的方法。

按实际交付对象写，而不是把代码目录当说明书。每个需维护的配置文件/表、任务、Action、页面、接口至少说清：在哪里操作、填什么或触发什么、作用范围、最小验证、失败处理、停用/恢复。无关辅助类不必逐个列出。

配置与字段映射要说明方向、必填键、类型/默认值及提供方；只有合同已确认才给完整可复制的脱敏 JSON/XML。来源没有定义的字段不能补成“示例默认值”。跨系统、异步或发布顺序用短流程表达；配置有多项比较才用表格。

交付草稿也要逐条核对事实：只知道“归档推送”时，不推定目标是财务系统、存在主明细或会发生入账；这类内容只能在本任务已有证据时写入，否则明确待确认。不要把另一项目或测试题的业务背景带入当前交付。

交付内容包括改动和发布物、实际验证、待现场验收、配置/部署建议、回滚与已知风险。不把本 Skill、AGENTS、本地知识根、自检记录或私有来源链接列作客户交付物。撰写部署说明不构成执行部署授权。

正式客户 HTML 按需读取 [交付文档模块](../skills/weaver-cc-delivery/MODULE.md)，使用随包模板、对象清单和校验器。用户要求 Word 时使用宿主已具备的文档能力；本模块不宣称提供 Word 渲染器。一般修改只给简短说明，不自动进入正式交付流程。
