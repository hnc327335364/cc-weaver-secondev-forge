# 需求、方案与估算

## 先把任务说清

从已给材料提取：谁、在哪个系统与入口、什么触发、输入输出、正常与异常结果、权限、不包含范围、如何验收。未知项标为待确认，原文事实、用户确认、建议分别写，不填造流程 ID、字段或默认业务规则。

不要求每个简单任务都填完整表。按实际场景检查容易遗漏的部分：重复提交与并发、跨系统超时/补偿、状态撤销与重做、主明细与历史数据、附件、PC/移动端、权限与审计。项目人员首轮只需回答影响当前结论的 1–3 个独立决策问题；不要把多个决策、字段清单、版本和环境要求藏在一个编号里。其他材料在进入相应开发阶段时再收集，不要求本轮全部答完；影响安全或估算成立的缺口仍须明确，不能为了少问而假定已有。

已确认口径继续有效。新事实与旧结论冲突时指出冲突、影响及需要谁确认，不悄悄覆盖、不重新询问所有已回答的问题。业务裁决和技术契约确认分开。

## 保留事实与阶段边界

已提供材料先提取，维护已确认、暂定、待验证和排除项，不反复追问原文。选项 ID、单位、金额口径和日期类型分别核对；某一字段原值写入不推广到全表。用户排除的能力不以预留字段、空实现或“以后可能用”重新加入。

| 缺少项 | 实际影响 |
|---|---|
| 需求目标、数据含义、失败/重复处理未定 | 影响对应方案和实现；其余无关部分可继续 |
| 平台方法、请求/响应结构未知 | 阻塞依赖它的可运行调用，不能造方法或映射 |
| 真实账号、密钥、网络 | 阻塞真实联调；已知协议可实现并做离线验证 |
| 部署窗口、审批、服务重启条件 | 阻塞发布，不等于需求分析或本地编码不可开始 |

无配置跳过、失败放行、先删后插等影响数据的行为必须有本项目依据。用户提出方案需求时，将建议写成建议；未经确认不提升为既定设计或长期记忆。

## 方案选择

1. 先核对标准配置能否满足当前目标；有证据时给配置方向、限制和验收，不为了展示能力增加代码。
2. 确需低代码时核对现有模块能力与权限；配置说明不能当作 API 合同。
3. 只有明确差异才进入二开，列出实际改动点、依赖、风险和验收。未找到配置能力不等于证明必须二开。

简单场景用一段结论；多个方案确实需要比较时再用小表。流程含状态、分支、异步或跨系统时序时给简短流程，不能把未确认分支画成事实。

## 估算

按可交付工作项拆分，分别列开发、联调/验证、文档与风险预留；用区间表达不确定性，写明假设、不包含项和依赖。外部等待不是已经消耗的开发人天，单独说明对日历工期的影响。

若已读取历史基准，可注明其来源、样本/校准限制并按当前范围修正。没有基准也可给明确标为经验初估的区间，但不能冒充历史统计、报价或排期承诺。未知接口和现场条件不能仅乘一个系数就算已解决。

## 输出与交接

默认先给项目人员可用于本轮决策的短结论：当前建议做什么、交付什么、哪些条件尚未成立；需要工时时紧接工作项区间与关键假设，再问当前必须拍板的问题。保留一句可观察的验收标准，包含本期明确不能改变的业务状态。实现阶段才需要的材料另列为后续收集，不展开完整技术问卷。避免在背景、风险、估算和结尾重复同一组事实；详细状态设计、字段清单与完整验收用例在用户要求或进入相应阶段时展开。用户未要求正式文档时，不默认生成 DOCX、长 JSON 或多份重复文件。

实现前把已确认目标、字段/接口证据、授权范围、待确认项、验收点沿用给开发任务，不让使用人员重新填表。材料不足时说明可以先完成哪部分，而不是一律判整个需求不可做。
