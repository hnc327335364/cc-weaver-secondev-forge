# E10二开不生效与运行错误定位

> 随包解释卡，供内部试用。通用正文、API、案例与已有本地附件先查 [资料导航](../library/catalog.md)，按标题或符号检索后使用 document_id 读取；不依赖维护者电脑路径。本页的核读日期、数量与行号描述当时的整理范围，不代表当前整库验收。详细维护记录不随包，客户工程与现场配置另行提供；知识卡指纹见 [manifest.json](manifest.json)。

先区分 **代码未加载、代码已加载但未执行、已执行但实例/范围/契约不匹配、服务端拒绝或失败**。这四种情况不能靠同一套“刷新、延时、重新发布”处理。本页提供七张排查卡；先用症状选一张，不要求从头读完整套手册。

**适用范围**：E10 e-code 前后端及表单/流程 SDK。工具包 `1.3.4` 是资料工具包版本，不是客户 E10 基线。以下为来源核对后的诊断方法，未做客户现场、发布、权限修改或服务重启验证。源文件仍只读；来源中的示例凭据、内部地址、截图未搬入本页。

## 先取得这五组证据

1. **环境**：E10 完整基线、部署模式、PC/移动端、登录前/后、当前租户与人员角色（只记录脱敏标识）。
2. **入口**：Ecode 应用、页面/表单设计器代码块、业务事件 JavaScript、门户主题、流程自定义入口，具体属于哪一种；最后正常时间及最近改动。
3. **范围**：应用发布状态、发布端、公共/租户类型、生效人员/角色；页面路由与当前组件/表单归属。业务事件 JavaScript 不等同于 Ecode 代码块，应按所属业务模块诊断。[H03:239–256]
4. **运行**：真实加载文件中的目标代码、首个相关错误堆栈、请求时间/方法/脱敏路径/状态码/业务错误码；不要只给“控制台没输出”。
5. **对照**：同环境目标/非目标页面、正常/异常人员的差异；需要屏蔽、重新发布、改权限、重启或重放写请求时，先确认授权和影响范围。

没有环境或入口事实时，先问缺少的关键项；缺日志不能宣布“平台 bug”，搜到源码也不能宣布“执行成功”。下列顺序是部门整理的诊断决策，不是未经验证的自动修复脚本。

## T01｜发布后没效果、只有部分端或人员生效

**先看**：发布清单与入口前置标记 → 浏览器实际加载内容 → `global` 与 `ecodestatic` 请求 → 错误堆栈 → 缓存/范围。

- **没有入口执行证据**：确认 `entry.js` 是否是实际入口、是否前置加载。资料说明：仅有可引用模块、没有前置入口的项目可以被别的应用引用，但不会自行执行；不能因为文件叫 `entry.js` 或应用显示已发布就跳过该检查。[L01:774–808]
- **搜不到目标代码，或搜到应用但内容仍旧**：记录该次业务页面刷新时的实际资源路径、响应状态及内容标识，再查 `global`/`ecodestatic`。`404` 指向资源交付链候选；由运维核对存储/挂载/节点，**不能仅凭 404 判定 NFS 损坏或直接重启 nginx**。[H03:10–114]
- **目标代码已在实际资源中**：转查入口执行、范围判断和首个异常。代码存在只排除了“该响应没带代码”，不证明回调注册、组件渲染或业务分支执行。[H03:18–28、152–182、226–233]
- **仅免登/外部分发失败**：先分普通应用和设计器代码块。普通租户应用与公共应用加载范围不同；切为公共应用是影响范围扩大，须审批，不能当默认修复。设计器外部分发另有 `10.0.2312.02` 基线及新旧 `index.js` 地址条件，不能混用普通应用结论。[H03:117–147、250–256]
- **仅 PC/移动或部分人员失败**：对照实际发布端 `P/M/ALL` 和应用生效范围。不要由 PC 成功推断移动端通过，也不要靠扩大到所有人员“验证”。[H03:133–147、231–233]
- **稍后刷新才生效**：来源给出的观察项为 `/api/app/ecode/cache/global` 的 `refresh`、`globalData` 的 `cacheTimeout`；先从已有 Network 记录确认当前返回与资源更新时间。来源所述刷新次数/间隔是该机制的线索，非所有版本或故障的保证；不要直接降低全局缓存时间。[H03:189–221]

**PC 门户主题补充**：应用已发布之外，还要核对主题记录启用、使用范围和主题选择的应用。导入 Demo 不代表自动发布，标准主题配置也不保证在自定义主题实现；这份门户来源限定 PC，不能由此承诺移动主题行为。[L05:65–97]

## T02｜组件覆盖没命中、影响其他页面、替换后卡死

**证据**：目标真实组件库名、组件名、关键 props、路由、稳定标识；覆盖回调是否进入及命中哪一分支；替换前后堆栈和非目标页面表现。

1. 先按 T01 证实入口。再通过组件检查工具确认实际库名/组件名，不能从 DOM 标签猜组件。`regOvProps` 返回修改后的 props；未命中目标也要保留原 props。[H10:10–24；L01:370–400]
2. 回调已进入但条件未命中：核对 `weId` **末段**与业务 props、路由。完整拼接 `weId` 会随父级变化；末段也可能重复，因此不是单独的业务身份。不要为了命中删掉范围约束。[H07:30–55；L01:424–449]
3. 替换组件反复进入或栈溢出：检查是否在替代组件内又导入同一个被替换的公共组件，造成再次走覆盖。原文给出通过覆盖回调持有原组件再传入的处理路线；保留事件、props、ref 等原契约，不能仅删组件掩盖错误。[H07:308–367；H10:41–47]
4. 异步加载报错：检查实际模块导出、加载方式、`React.Suspense`，以及是否在前置入口直接使用 `@weapp/ui`；资料把前置入口与非前置组件分开。不要看到模块错误就盲目安装另一套 React。[H07:62–88；L01:452–454]
5. 新路由不显示但其他页面也异常：检查注册到 `Switch` 的外层与匹配范围。源文在其 `react-router v5` 场景中指出外层不是 `Route` 会截断后续匹配；先确认实际版本及路由树，不能把“增大权重”作为跨版本通用补丁。[H07:406–445]

**判断边界**：回调执行过不等于标准字段组件已经挂载；公共组件覆盖成功也不等于保存校验、权限和原事件保持正确。目标页、非目标页、首次打开及再次打开都应验证。

## T03｜SDK 实例为空/操作错表单，保存后事件失效或重复

**先区分**：表单 SDK 与流程详情 SDK；布局代码块与全局 Ecode；首次进入与保存后的再次渲染。记录取实例、注册事件、回调执行三者的顺序及页面归属，不记录业务字段明文。

- **取得错误表单/弹窗实例**：流程详情 `getFlowPageSDK()` 默认取当前活动详情，弹窗打开后可能已换实例；应使用当时已确认并持有的目标实例。表单 `formSdk` 闭包是特定入口能力，不是任意 Ecode 文件的全局变量。[L02:74–107；L03:63–98、1522–1533]
- **取实例过早**：按当前入口的 SDK 约定确认加载阶段。本库将表单闭包实例标为 `250101`，但工具包同源正文另一处写 `241201`；该冲突见 [E10表单SDK实例与字段操作示例补充](e10-form-sdk-examples.md) F01。未确认现场前不能按较早数字承诺可用，也不能给所有入口统一包 `formReady`。[L03:68–98、1553–1557；L04:73–95]
- **第一次能用，保存/提交后不再生效**：流程详情可能 URL 不变、仅重新渲染；来源中的 `onceReady` 只首次触发，`ready` 则包含再次渲染，但该章已标“不推荐”。按入口和具体事件契约选择，不把所有事件强塞进 `onceReady`，也不以固定延时替代生命周期证据。[L02:373–396]
- **一次动作触发多次**：查注册次数与 `fnNameCover`。流程 SDK 的拦截、钩子签名不同，钩子还含 `autoJudgeExecute`；不能复用参数位置。来源说明名称可防重复，但重名会导致覆盖，所以需业务隔离；“名字相同”不自动证明注册正确。[L02:242–255、315–331]
- **手改触发，联动带值不触发**：表单字段事件对联动值有单独扩展与版本条件：普通字段 `ext` 标 `250401`，明细事件标 `250901`，后续 `251101` 又有变化；新增/删除明细行不属于这些值变更范围。先核对当前基线、字段事件和现有行/新增行测试，不默认开启全局联动开关，更不能关闭全部校验消除循环。[L03:450–517]

**判断边界**：SDK 对象存在只证明对象可取；不证明对应数据已就绪、选对实例或所有方法在当前入口可用。E9 的字段事件/对象大小写不能套到 E10。

## T04｜请求失败、接口返回 403、拦截器不触发或影响其他接口

**证据**：当前基线；实际调用端；脱敏 URL/方法；HTTP 状态与业务体分别记录；准入名单中的准确接口及准入类型；回调是否执行。错误码相同不代表拒绝层相同。

1. `devRequest` / `regApiInterceptor` 来源明确支持 `10.0.2509.01`。低于或未知基线先核实当前能力，不直接套新 API，也不改用普通请求库绕过。[H06:1–3；H11:7–29]
2. 若响应含来源展示的 `ecodesdk secondev reuqest access interception`，首先查前端二开准入；它是一个已知特征，**不是所有 403 的解释**。`/api` 前缀本身不等于允许访问，`/papi` 示例也不等于可直连任意开放平台。[H06:43–63；H11:23–29]
3. 请求能发、拦截不执行：核对准入类型是否为“允许调用和拦截”，而非仅“允许调用”；再查入口、目标 URL 判断、稳定拦截器名及实际顺序。名单缺失应走所属模块确认，不能在客户前端解除限制。[H06:65–69、131–157]
4. 回调进入后其他请求坏了：检查每条分支是否返回原/修改后的 `config` 或 `response`，错误处理是否继续拒绝；非目标请求必须保持原样。旧规范中出现直接 axios 全局拦截示例，不能据此覆盖新准入封装规则。[H06:77–128；H07:555–581；H11:31–78]
5. 多拦截器顺序异常：原文参数表将请求和响应权重均写为从大到小；工具包精简卡又说响应链反向返回。这里存在表述差异，应以非敏感观察字段验证该环境实际顺序，不能写死某一推测再以此解释业务失败。[H06:118–125；H11:88]
6. 若后台明确报“接口未准予二开服务访问”：这是后端标准服务开放问题，需接口所属模块评估，不等同于前端名单。后端正常但前端解析失败，再核对路由、方法、参数及实际 `WeaResult` 结构，不凭示例补业务字段。[H03:965–967；H07:695–736；L01:67–81]

**禁止捷径**：不因“无权限”直接复制 FAQ 的 `publicPermission` 注解；先确认拒绝层与业务授权。不把接口改成公开路由，不把 Cookie/令牌贴进诊断文档，不重放尚未确认幂等性的写请求。[H03:829–834 为待上下文判断的原建议，不作通用结论]

## T05｜开发平台、监控平台、应用或下载提示无权限

**先分资源，再分身份**；能进入 Ecode 不等于有监控管理员、开发者下载或某应用的数据权限。

| 现象 | 优先核对的证据 | 下一分支 |
|---|---|---|
| “组织目前不支持此功能” | 当前租户状态、应用开通、Ecode 模块启用状态 | 属租户/功能范围候选，由管理员确认；不是先改业务代码。[H04:6–20] |
| “未登录或者未授权，无法访问 ecode” | 实际登录状态、当前角色的 Ecode 功能权限 | 权限项不存在时，来源给出 `10.0.2310.01` 门槛，先确认基线。[H04:28–40] |
| 开发平台能进，监控不能进 | 监控租户准入与管理员权限分开核对；确认主管理组织 | `10.0.2405.01` 前后配置入口不同；后者的配置保存还要核对重加载后的“一致”状态，不能仅看保存提示。[H04:70–104] |
| 能看平台却不能下载二开依赖/版本/日志 | 当前人员是否具开发者下载权限 | FAQ 单独要求开发人员权限；不要盲目扩大监控管理员名单。[H03:632–642] |
| EB 自定义组件打开代码开发提示无权限 | 分权/数据权限是否启用，项目维护权及既有组件应用权 | 已有组件还需其应用权限；不能只核对新建权限继承。[H03:1403–1415] |

**边界**：本页不执行赋权、配置重加载或节点重启。来源提醒多节点可能未全部刷新，需管理员核验各节点实际状态；不能只凭某一节点正常宣布修复。[H04:100–104]

## T06｜jar 上传/部署成功，但功能仍旧或运行报错

**排查链**：本地制品 → 上传/审核 → 目标服务与节点 → 实际同步/加载 → 请求到达 → 业务日志与返回。各环节各自举证，上传完成不是部署验收。

1. 上传阶段报缺 `weaver-ecode-seconddev-id`：检查是否使用对应标准模板/插件生成，核对制品清单和标识；不要手补一个随机标识让校验通过。原文同时存在非插件标准模板路线，因此不能概括成“所有非插件构建都不可用”。[H03:477–481、645–661；H07:750–782；L01:83–102]
2. 报缺 Java 源文件：来源从 `10.0.2409.01` 增加源码校验，先查实际包内容和打包模板。内部类细分类依赖原文图片，**本页未核验图片内容，不推导“所有内部类都必须拆分”**。[H03:645–676]
3. 平台显示已部署但服务还是旧逻辑：由运维核对目标服务、节点、实际制品指纹及同步记录。FAQ 提醒特定同步机制依赖运维平台重启，脚本手动重启不触发；应确认当前机制和运维平台基线显示，再决定经授权的操作，不能在未知部署模式下循环重启。[H03:976–990]
4. jar 已确认同步且载入：转查入口注册、配置、接口是否到达及首个异常；不再反复上传相同包。三方依赖另有 `<10.0.2411.01` 与 `>=10.0.2411.01` 路线差异，依赖上传不等于已生效。[H03:1082–1105]
5. 查日志前先确认类包路径和来源版本：原文针对 `com.weaver.seconddev`，`250301` 前错误日志为 `sys-err.log`，从 `250301` 起为 `sys-seconddev-err.log`；两者 info 均为 `sys-seconddev.log`。来源使用此短版本写法，现场需对应到实际基线，不能因查错文件而说“后台没有异常”。[H03:1005–1032]

**判断边界**：日志文件名、模板约定与文档一致不证明当前服务真的加载目标版本；本页未编译任何客户工程，也未上传、发布、重启或调用现场接口。

## T07｜怀疑二开影响标准功能：如何做有意义的屏蔽对照

屏蔽会改变运行行为，必须由有权限人员在确认的页面/人员/租户范围内执行；本页不自动申请授权码或发布调试代码。先保留未屏蔽的复现步骤、错误与时间，再一次只改变一个候选应用/资源，最后恢复并核验。[H05:9–22、62–76]

| 来源版本条件 | 原文能力 | 不应混用的结论 |
|---|---|---|
| 支持基线 `10.0.2502.01`；早期说明 | 授权码一次调试/首次刷新屏蔽，后续失效 | 不能拿旧“一次性”规则解释新版持续屏蔽。[H05:3–5、29–45] |
| `10.0.2507.01` 变更 | 去除地址栏授权码方式；可设置有效时长，有效期内持续使用 | 不再照抄旧地址栏授权码方案；普通调试工具显示参数与授权码参数不是一回事。[H05:84–98] |
| 同一新版 | 按资源路径或应用屏蔽；恢复/清除后刷新 | 应用维度只让前置 JS 不生效，**不会屏蔽前置 CSS**。样式问题仍在不能直接排除该应用。[H05:103–118] |

- 提示授权码不存在/失效/配置不符：按租户与人员、指定页面完整地址、有效期逐项核对，不绕过校验。[H05:62–66]
- 屏蔽后恢复正常：仅说明该候选或其依赖/相互作用与问题有关，仍需回到具体代码和调用链，不能立即归因到某一行。
- 屏蔽后仍异常：先证实屏蔽成功及覆盖 JS/CSS 范围、刷新生效、测试条件一致，再缩小其他候选。所有二开全关也不能证明标准代码无 bug。
- 调试后恢复禁用项、清除临时调试开关并复测目标/非目标页面；保留脱敏的屏蔽日志与对照结果，不将授权码写入交付物。[H05:50–54、70–76、103–118]

## 对外报告的最小结论
