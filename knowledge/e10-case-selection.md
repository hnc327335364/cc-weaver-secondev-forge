## 结论和使用边界

工具包案例适合提供**实现位置和调用结构**，不宜按标题整包复制。此次选取 5 个不同需求，逐个读了记录正文及其全部 13 个声明源文件；既保留可复用模式，也记录能从源码直接确认的问题。记录文字多为简短标题复述，以下判断主要来自实际代码，不把案例名称当实现证明。

核对日期：2026-10-21；执行：Codex 静态整理。13 个源码 SHA-256 与记录声明一致；完整记录/源码路径、`caseId`、`verId`、`sourceId`、SHA-256 见 来源证据 JSON（来源记录，未随包）。**未运行工具包代码，未编译发布，未做客户、PC/移动或宿主验收。** `1.3.4` 是工具包版本，不是 E10 产品基线；4 个案例未填系统版本，不能据此推断当前租户兼容。

| 需求 | 选用案例 | 现在可采用什么 | 必须排除的误用 |
| --- | --- | --- | --- |
| 主表选择分类，明细按对应分类汇总金额 | C1 条件汇总 | dataKey 转字段、遍历当前明细行、条件累计后回写一个主字段 | 原样用于小数金额、首次打开和删行后自动正确 |

## C1：条件匹配的明细金额汇总

来源：`786346144923262976` / `786346144923262977`（case/ver）；源码 `resources/entry.js`，`sourceId=6860e376c0cbfbb5`。记录平台 PC；系统版本空缺。

**适用判断：**同一 E10 表单内，主表分类与明细分类使用不同的保存值，需要建立映射，只把匹配行金额加到主表。若只是无条件合计，先评估标准公式；无需为了复用案例增加入口覆盖和轮询。

| 必须从目标表单确认 | 原例如何使用 |
| --- | --- |
| 主表分类 dataKey、主表合计 dataKey | 第 10–13、32 行转换字段并读取/回写 |
| 明细容器 dataKey 与明细分类、金额列的归属 | 第 19–23 行取明细行号、转换列字段 |
| 主分类保存值 → 明细分类保存值映射 | 第 14–17、27 行按映射比较；不是按显示文本比较 |
| 金额精度、空值/非法值、是否允许负数 | 原例仅有空值转 0，没有完整数值规则 |

可复用链路：`convertFieldNameToId` → `getDetailAllRowIndexStr` → 读取 `${列字段标识}_${行标识}` → 按类型匹配 → `changeFieldValue` 回写主字段。原例会从 0 重新累计，分类改为无匹配时可得到 0；不应沿用旧合计。

**源码明确问题与改造：**

- 第 28 行 `parseInt` 会截去每笔小数，不能用于金额精度要求。需先明确目标字段/平台的数值表示及舍入规则，再采用合适的十进制运算或最小货币单位；不能简单宣称换成浮点累加就解决所有金额精度问题。
- 第 47–54 行只注册字段变更，没有首次初始化调用，也没有明细新增/删除动作处理。源码无法支持“已有数据首次打开”和“删除整行但金额字段未另发变更事件”这两个验收结论。
- 第 22–23、52–53 行转换明细列未传明细归属；主明细存在同名 dataKey 时需按当前 SDK 契约明确表归属。原例使用通用 `bindFieldChangeEvent` 监听明细列，不能据此认定所有基线都会按预期触发；用目标基线已确认的明细事件合同。
- 第 35–61 行借 `Title` 的完整 `weId` 命中再轮询实例，用模块级 `times` 只执行一次，异常被吞掉。多表单/重新打开是否漏绑必须验证；优先改挂实际表单入口和 ready 生命周期，不复制这套轮询。

**改造后的验收清单（尚未执行）：**已有明细首开即合计；分类切换匹配/无匹配；金额含两位小数、负数、空值；编辑分类/金额、新增/删除行均重新计算；同页两个表单互不串值；关闭后重开不漏事件或重复计算。需要跨表/后端金额一致性时，此纯前端案例不足。

## C2：菜单与多级自定义路由

来源：`761844820988346368` / `761844820988346369`。实读 `entry.js`、`index.js`、`pages/a.js`、`pages/b.js` 共 4 文件；记录平台 PC，系统版本空缺。入口 `sourceId=136632ad5386ffe4`。

**适用判断：**需要在已有门户中增加一级菜单及两个子页面，业务页面可独立异步加载。若只需配置外链、标准页面导航或 EB 页面，先用标准菜单/页面能力；不要为几个链接自建路由层。

可复用结构：

1. `entry.js:9–19` 用 `React.lazy` + `asyncImport` 分别加载 3 个页面模块；`index.js` 和两个子页面各导出 React 组件。
2. `entry.js:39–61` 用 `Route` 和 `regOvProps('weappLayout', 'ModuleRouteContent', ...)` 扩展内容区。
3. `entry.js:64–96` 生成带 `children` 的菜单树，通过 `Main.beforeUpdateAsideMenus` 保留原回调后追加菜单。

需要配置：实际 e-code 应用标识、模块相对路径、目标门户/容器、3 个唯一菜单 ID、3 个不冲突的路由、目标宿主的 router API 版本。原例 `${appId}` 是导出模板字符串，不能当实际应用标识；是否由平台导入时替换需检查导入结果。

**源码明确问题与改造：**

- 第 7 行读取了 `publicUrl`，第 39–41、69–81 行仍写死门户根路由，没有用它拼接。部署带前缀、多应用挂载时需根据实际 `appInfo`/路由方式统一构造，不能仅替换菜单文本。
- 第 43–50 行直接变更 `props.children`，第 65 行无去重追加菜单；第 91 行每次再次包装旧回调。需验证重复加载/重渲染是否重复路由或菜单，改为按稳定 key 去重并保持非目标内容。
- 第 23、29、35 行 `Suspense.fallback` 传函数而不是明确的可渲染占位内容；按当前 React 版本改为 `null` 或实际 loading 元素。入口未显式导入 React，只能在现场确认平台是否提供全局 React，不能假定普通打包环境可用。
- 三个页面源码分别只渲染 `Index`、`a`、`B` 文本，没有数据读取、业务操作和权限逻辑。只能作为页面骨架，不宜据此估算“业务页面已经实现”。

**改造后的验收清单（尚未执行）：**从菜单进入每页、直接访问、刷新、后退；含部署前缀的地址；模块加载失败提示；重复进入后菜单/路由不重复；非目标门户无变化；有权/无权用户分别验证真正的数据接口权限。移动端和不同 router 版本不在该 PC 例的已证范围。

## C3：EB 选中行带值打开流程创建页

来源：`795789794401886208` / `795789794401886209`。实读 `entry.js`、`button.js`、`index.css`；记录平台 PC，系统版本空缺。核心按钮 `sourceId=44f1719159fe4cbf`。

**适用判断：**用户从一个指定 EB 台账手工选择一条记录，打开流程创建页面并预填一个字段，随后由用户检查和提交。它不是后台发起流程接口，也不是批量集成、事务同步或“点一次就创建成功”。

可复用链路：入口异步加载按钮 → 限定目标 `Title`/应用 → `getCheckIds()` 校验恰好一条 → `getListDatas()` 匹配 `ebrecord_rowkey` → 读取来源字段 → 打开已确认的创建页，并映射到目标流程字段。

| 目标项目应建立的映射 | 原例位置 |
| --- | --- |
| 台账视图/实例 → SDK，而非全局任意列表 | `button.js:10–12` 使用 `window.ebdfListSdk` |
| 选中 ID 类型 → 当前行主键类型 | `button.js:18` 用 `ids.includes(x.ebrecord_rowkey)` |
| 来源 dataKey/列 → 目标流程字段标识 | `button.js:21–22` 固定一个来源列和一个目标字段 |
| 流程定义/创建路由 → 当前租户和基线 | `button.js:22` 固定创建路由及流程 ID |

**源码明确问题与改造：**

- `getListDatas()` 返回可取得的列表数据不等于所有已选跨页记录。第 18 行 `find` 可能无结果，第 21 行随即访问属性，没有空值分支。要么限制当前页选择并说明，要么用已确认且受权限控制的记录读取接口；不要猜新接口。
- 第 22 行直接拼接字段值，没有 URL 编码。`&`、`#`、`+`、中文等值需按实际创建页参数契约编码；敏感/长内容不宜放地址栏，应另选获授权的数据传递方式。
- `entry.js:15` 在命中目标之前给所有经过该覆盖的 `Title` 添加 class；第 19 行直接 `splice` 插按钮且未防重复。把 class、按钮及其样式全部限制在目标容器，稳定 key 去重。
- 全局 SDK 与选中值类型都需实测，目标为多列表页面时优先确认可定位 view 的 SDK；不能把此旧全局变量当所有 E10 页面的通用入口。

**改造后的验收清单（尚未执行）：**未选/多选/恰好一条；跨页选择或记录已不在当前数据中；无权限记录；值含特殊字符；创建页字段实际预填；用户取消不产生“已创建”回写；非目标列表不出现按钮/class。若需求包含来源记录状态回写、唯一防重或后台自动发起，另设计服务端闭环。

## C4：受限接口响应展示修正

来源：`1076434309112528899` / **`1100440144067297285`**（case 与当前 ver 不同）。记录平台 ALL，建议版本 `10.0.2410.01`；不等于已在所有终端验证。实读 `entry.js`（`sourceId=453b0e9f52186bf9`）与 `readme.md`（`sourceId=55af0ae4c12bfb02`）。

**适用判断：**目标页面确实通过同一个可访问 Axios 实例发出已知请求，需要展示层增补或兼容处理。若请求走另一个 Axios 实例、fetch、RPC 或移动原生桥，此拦截器可能完全看不到请求；必须先沿实际调用链确认。

可复用结构：`axios.interceptors.response.use(success, failure)`；成功回调检查 `response.config` 和 `response.data` 后返回响应；错误回调 `Promise.reject(error)`，保留失败链。它不提供后端接口、权限和可靠的数据修正服务。

**必须分清两个来源版本的内容：**

| 文件 | 真正实现 |
| --- | --- |
| `entry.js:8–19` | 用 `url.includes(...)` 与 `data?.code === 200` 筛一个路径；命中分支只有注释，没有任何数据附加逻辑；失败打印 error 后继续 reject |
| `readme.md:8–24` | 遍历 `appendResponseData`、`url.startsWith(k)`、`Object.assign(response.data, ...)`；片段内未定义映射变量，也未给 Axios import/配置 |

**改造要求：**根据真实 HTTP method、解析后的 pathname、目标页面和已知业务条件限域；不能仅靠任意子串匹配。确认响应是预期对象和字段结构后再做最小展示转换，不在原对象上盲目合并；保留未知响应和非目标请求。保存注册返回的标识并使用目标 Axios 实例已确认的卸载能力，防止多次进入重复拦截。原例未提供防重或卸载。避免原例对整个 `error`、`response.data` 的打印，以免请求头、用户数据或票据落日志。

**改造后的验收清单（尚未执行）：**目标与相似但不相同路径；目标成功、业务失败、网络失败；空值/字符串/二进制等非预期响应；请求实例确实经过拦截；重复加载只执行一次；非目标对象不被污染。只读展示改写不得承诺服务器已保存或已校验。

## C5：E10 → E9 单点登录按钮（排除完整方案误用）

来源：`761508353320296448` / `761508353320296449`。实读 `entry.js`、`index.js`、`index.css`；记录平台 PC，系统版本空缺。按钮 `sourceId=d86c0c98e66170a9`。

**适用判断：**已经有获批准的服务端单点集成，只缺 E10 前端入口，可参考“点击 → 调服务端函数 → 判断结果 → 打开返回地址”分层。若目前没有账号映射、签发/兑换票据或 E9 服务端接入，本案例应被排除为完整实现模板。

实际代码与标题存在差别：

- `entry.js:1–53` 的菜单 store 修改方案全部是注释；实际执行的第 55–68 行创建 DOM 容器追加到 `document.body`，再渲染按钮。样式把它固定在页面左下角，并不是有效代码已经注册标准菜单。
- `index.js:9–19` 向一个 serverless 执行端点发请求，携带 token 占位符和固定函数标识，再打开 `funcRes.data.url`。该记录的 3 个源文件**没有服务端函数实现**，不能验证票据算法、账号映射、有效期或 E9 认证机制。
- 源码 token 已是占位符；注释中还有固定租户标识，正文不复制这些租户/实例值。既不能把占位符当可用凭据，也不应要求把长期密钥填进前端。

**源码明确问题与改造：**

1. `entry.js:59–61` 无容器查重、路由限制或卸载，重复执行可能产生多个同 ID 容器；优先使用已确认的标准菜单扩展点，并明确目标范围。
2. `index.js:15` 仅检查 HTTP 200 和业务 code 的真值；第 18 行仅处理内层成功/失败，外层失败、结构缺失和请求异常没有完整分支。需按实际返回合同精确判断，并给用户可恢复的错误提示。
3. 第 16 行打印整个返回体，可能暴露跳转票据；第 19 行直接打开服务端返回 URL，没有来源/协议校验。服务端与前端均需按安全约定限制允许的目标；不在日志、交付物中记录完整票据地址。
4. 异步完成后才 `window.open`，浏览器拦截弹窗与用户取消的表现需实测，不能声称必定打开。`index.css:17` 使用全角冒号，不能表达预期 CSS `:hover` 伪类，应修正。

**开展集成前必须拿到：**服务端实现/接口合同、当前用户身份取得方式、E9 账号映射和接入规则、一次性票据/重放保护约定、允许的跳转目标、失败及登出策略。上述材料缺失时，只评估前端入口工时，不把 SSO 服务端和安全验收算作已有。

**改造后的验收清单（尚未执行）：**成功身份匹配；无映射/停用账号；过期及重复兑换；服务端失败/结构错误；未授权目标 URL 被拒绝；刷新重开无重复按钮；日志无票据；浏览器弹窗拦截有可用提示。跨域票据与 E9 实际接入均需现场授权验证。

## 如何使用这些卡完成一次需求选型

项目人员先按首表找到候选，将“适用判断”与实际需求对照；开发人员再读取该案例的真实文件和相关 SDK 参数手册，形成最小修改清单。只有确认契约后才编写请求或字段代码。以上列出的是改造方向，不是已经修复的源码，也不是可直接粘贴上线的代码。
