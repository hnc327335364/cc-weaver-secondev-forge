# E9后端改动与验收边界

> 随包解释卡，供内部试用。通用正文、API、案例与已有本地附件先查 [资料导航](../library/catalog.md)，按标题或符号检索后使用 document_id 读取；不依赖维护者电脑路径。本页的核读日期、数量与行号描述当时的整理范围，不代表当前整库验收。详细维护记录不随包，客户工程与现场配置另行提供；知识卡指纹见 [manifest.json](manifest.json)。

## 结论与适用范围

**以当前项目、现场 SDK 和实际节点时机为准；参数化 SQL 不等于事务已覆盖全部写入，本地通过也不等于客户业务通过。**

本卡是开发稿。平台方法总结与 Action 专题未给出可核实的完整版本区间，Action 原私有来源已移除；环境搭建原文标注 2020.5.29、文档版本 1.0，不代表当前所有 E9 的依赖要求。项目记录只支撑其中已说明的实现经验，客户现场仍待验证，不能外推为所有安装环境的产品合同。

本卡区分“已读资料记录”与“部门实施门槛”，不提供缺少目标 SDK、字段或配置时可直接运行的后端代码。

## 1. 先确认真正的执行入口

| 场景 | 已读资料记录的接口/方法 | 开始改动前要补齐 |
|---|---|---|
| 流程附加操作 | `weaver.interfaces.workflow.action.Action`；`execute(RequestInfo request)` 返回 `String` | 真实挂接节点、前/后附加时机、操作类型、Action 顺序及异常处理 |
| 建模页面扩展 | `AbstractModeExpandJavaCode`；`doModeExpand(Map<String, Object> param)` | 真实扩展配置、参数形态和空值；不能把流程 `RequestInfo` 当作必然存在 |
| 计划任务 | `weaver.interfaces.schedule.BaseCronJob`；`execute()` | 启停、调度、重复执行/并发、增量水位、重试和失败恢复 |

方法总结记录了 `RequestInfo` 的请求 ID、流程 ID、主明细字段，以及 `RequestManager` 的操作类型、表名、业务 ID 和用户。应核对当前入口实际可取内容，不把“资料列出可取”当作“任意节点都已生成或已落库”。

Action 专题提醒：上一节点 Action 查询当前操作者记录，未必能得到尚未计算或生成的下一节点操作者；发起节点未保存时，直接查表也不保证读到当前页面输入。涉及此类时机先取得真实调用链和样本，不能靠换表或轮询掩盖未知合同。

## 2. SQL：值与标识符分开处理

已读方法总结记录了本地库 `RecordSet` 的参数化 `executeQuery(String sql, Object... args)`、`executeUpdate(String sql, Object... args)`，以及 `next()`、`getString(columnName)` 等读取方式。具体重载、返回类型及异常行为仍需以当前 SDK/编译类核实；本卡不沿用源稿中未经源码核对的返回值描述。

部门实施门槛：

1. **值使用参数绑定**：用户输入、接口返回和配置中的业务值不能直接拼入 SQL；校验格式不能替代参数化。
2. **动态表名/列名单独约束**：标识符不能当作普通值占位绑定。优先固定；必须动态时，采用允许集合或严格标识符校验，并与真实流程/建模元数据核对归属和存在性。不能仅因字符串符合格式就允许任意表列。
3. **范围来自已确认业务键**：明确当前请求、模块和主记录的作用范围。清空/重建明细不能退化成全表删除；目标模块、表、字段尚不明确时只交付待确认项，不试探性写库。
4. **外部数据源另核合同**：资料中的 `RecordSetDataSource` 是集成中心外部数据源入口，不能把本地 `RecordSet` 的重载照搬过去。只看到 `execute(sql)` 不能批准拼接未经约束的输入，应先确认现场支持的参数化访问能力。
5. **建模业务链不能只看物理表**：创建人、模块信息、权限和其他标准链路须核对。不能因为 INSERT 成功，就宣称记录可见、权限正确或建模新增完成。

这些安全要求来自部门开发规则及已记录的局部实践，不是对全部 E9 数据访问实现的重新定义。

## 3. 事务范围必须能证明

方法总结记录 `RecordSetTrans` 的 `setAutoCommit(false)`、参数化 `executeUpdate`、`commit()`、`rollback()`。这证明资料提供了事务入口，不证明当前调用链的全部方法自动加入该事务。

要承诺“整批成功或全部回滚”，至少检查：

- 所有预校验完成后再开始受控写入；每一笔属于该原子操作的写入都实际使用同一事务上下文。
- 辅助方法是否内部新建连接、独立提交或忽略传入事务；方法参数里出现事务对象不等于实际使用。
- 中间写入失败是否传播到统一回滚路径；不能只记日志然后提交已写成功的部分。
- 外部 HTTP 调用、消息、权限重建和流程流转是否在事务之外；分别设计幂等、补偿或人工恢复，不声称本地数据库回滚会撤销远程动作。
- 提交返回异常或连接中断时，最终状态可能未知；先核对业务键对应的真实结果，不自动重复推送或重新导入。

已读项目记录曾在特定标准类中发现新增方法未按传入事务参与写入，因而对该项目调整实现；这只是提醒必须查实际源码，不允许推广为“所有标准新增 API 都不支持事务”。同一记录把提交后的权限重建、后续流程失败与已提交业务数据明确分开。

优先沿用当前项目已验证的标准业务入口；发现原子性与标准业务链冲突时，报告具体差异并确认方案，不能自行改成直接写标准系统表。

## 4. Action 返回、提示和回滚是不同合同

源方法总结把 `Action.FAILURE_AND_CONTINUE` 解释为“失败但继续”；本卡**不据此断言流程一定继续**，也不根据常量英文名推导阻断行为。要核对现场常量值、调用者如何处理返回值、`setMessagecontent`/`setMessageid`、节点挂接时机，并在目标操作下实测错误提示与流程停留位置。

Action 专题记录 `RollBackAction.executeRollBack(RequestInfo requestInfo)`，同时提示后续 Action 失败与后续流转失败可能走不同路径。因此：

- 实现回滚接口，不等于任意失败都必然触发它。
- 自己创建的数据库事务，不等于自动加入整个流程的事务。
- 本地业务已提交后，后续退回、撤回或另一 Action 失败，不等于已提交数据自动恢复。
- 远程系统成功而本地失败时，需要独立的幂等和补偿依据；禁止未经核对直接重放有副作用请求。

不要为“让流程通过”直接切换管理员、强制归档或改操作者。此类行为会改变审批与授权语义，必须单独确认范围、权限、审计和恢复方式。

## 5. 验证与交付分层

| 验证层 | 可以说明 | 不能说明 |
|---|---|---|
| 静态审查 | 已检查配置、调用链、字段映射、SQL 和失败路径 | 代码可在客户环境运行 |
| 目标依赖编译 | 使用明确版本的 JDK/SDK/依赖完成编译 | 节点时机、权限、事务结果已正确 |
| 单元或模拟测试 | 本次输入和测试替身下逻辑符合断言 | 真实驱动、平台缓存、隔离级别、权限接口已验证 |
| 测试环境联调 | 已在记录版本/配置下验证指定接口与业务路径 | 未测终端、其他客户、生产数据或所有失败场景正确 |
| 业务验收 | 用户按约定场景确认结果及回退边界 | 自动授权正式发布或后续扩展 |

至少给出正常、空值、非法值、中途失败、重复/并发、权限和非目标范围的适用测试。涉及整批回滚，要故意令后续写入失败并核对前面写入结果；涉及提交状态不明，先查目标状态。哪些场景不适用也需说明。

交付应包含改动文件、实际发布位置、配置填写规则、已执行验证、未测项、失败排查、停用及恢复步骤。删除代码不恢复已改业务数据；配置停用、制品回退、业务数据恢复要分别说明。日志保留请求标识、阶段、数量、错误码和脱敏异常，不记录完整凭据或原始敏感业务报文。

本轮只完成资料核对与知识卡编写，未编译项目、未接入 E9、未执行数据库/流程操作、未做客户验收。
