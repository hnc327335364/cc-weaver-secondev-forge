# E9表单前端生命周期与平台分流

> 随包解释卡，供内部试用。通用正文、API、案例与已有本地附件先查 [资料导航](../library/catalog.md)，按标题或符号检索后使用 document_id 读取；不依赖维护者电脑路径。本页的核读日期、数量与行号描述当时的整理范围，不代表当前整库验收。详细维护记录不随包，客户工程与现场配置另行提供；知识卡指纹见 [manifest.json](manifest.json)。

## 结论与适用范围

**先确认页面类型，再选择对象；首屏初始化与后续事件要分别处理。** 新增行事件不能代替既有行初始化，字段变化事件也不表示打开页面时已执行过一次。

本卡是部门助手的精简开发稿，不是完整 API 文档或现场验证结论。接口事实来自本地流程、建模 API 正文；两份资料记录抓取日期为 2026-05-08，原桌面文件已失效。ecode 说明也缺可核实原件。本轮没有联网复核官方页面，没有取得目标现场版本、模板、源码或运行日志。

下文明确区分“资料合同”与“实施要求”。列出的最低 KB 只属于对应接口，不能当作整页或整个 E9 的统一适用版本。

## 1. 平台与入口分流

| 当前对象 | 应先核对的入口 | 不可直接套用 |
|---|---|---|
| E9 流程表单 | `window.WfForm`、节点模板代码块或路径自定义页面 | 建模卡片的 `ModeForm`、查询列表接口 |
| E9 建模卡片 | `window.ModeForm`、卡片的实际加载入口 | 流程保存/提交常量、流程路径配置 |
| E9 建模查询列表 | 建模 API 文档的查询列表部分及真实页面上下文 | 仅因同属建模就套用卡片字段生命周期 |
| ecode 页面或组件扩展 | 发布文件夹、前置加载/异步组件加载及业务绑定 | 把前置脚本执行当成表单字段、组件已经就绪 |

资料说明：ecode 前置加载发生在系统和组件加载之前；发布成功的文件并不默认加载。先证明代码在目标页面被加载，再证明对象及目标数据已就绪，最后才判断业务逻辑。

流程文档列出的自定义页面有不同范围：节点模板代码块、某路径下各节点模板、全局非模板场景。全局自定义页面特别提示避免定义 `ready`、`checkCustomize` 等全局函数；不能把某节点的初始化代码直接推广到全局。

## 2. 已核对的字段与明细合同

以下方法名在两份表单 API 正文均有记录，调用对象必须按上表确定；相似方法不代表所有参数、事件或版本都可互换。

| 目的 | 资料合同 | 容易误用处 |
|---|---|---|
| 字段名转标识 | `convertFieldNameToId(fieldname, symbol, prefix)`；主表默认 `main`，明细如 `detail_1` | 先核对现场字段数据库名；不要跨环境写死页面字段 ID |
| 枚举现有明细 | `getDetailAllRowIndexStr(detailMark)` 返回逗号分隔行标识 | 行标识可能不连续；跳过空串，不能用数组位置或总行数代替 |
| 读取一行字段 | `getFieldValue(fieldMark)`；明细字段标识含下划线和行标识 | 页面行标识不等于数据库主键，也不是肉眼看到的“第几行” |
| 绑定指定字段变化 | `bindFieldChangeEvent(fieldMarkStr, fn)`；回调为 `(obj, id, value)` | 可以绑定具体明细字段，但不是覆盖全部行的默认办法 |
| 绑定明细列变化 | `bindDetailFieldChangeEvent(fieldMarkStr, fn)`；列标识不带下划线；回调为 `(id, rowIndex, value)` | 覆盖已有行及后续新增行的“值变化”，不等于自动补跑首屏逻辑 |

流程资料的 `changeFieldValue` 明确不支持附件类型，并提示后台只读字段在非创建时刻的改值可能不入库。显示变化不等于业务数据已保存；不要借前端改属性绕过后台只读或权限配置。

## 3. 首屏、增删改与提交分开设计

以下是依据事件合同形成的实施要求，不是新增平台 API：

1. **定位作用范围**：确认平台、页面、流程/模块、节点、主明细字段及 PC/移动端；非目标页面直接保持原状。
2. **初始化一次**：在现场已确认的表单数据就绪时机，枚举全部既有行，对每行执行本次计算或显示规则。资料没有给出可覆盖所有入口的统一“就绪”接口，不杜撰名称，也不把固定延时当成可靠保证。
3. **后续新增**：注册对应明细的新增完成事件，为新增数据补处理；批量新增的回调形态须现场核对，不能假设每次只有一个数字下标。
4. **后续修改**：绑定实际依赖列的值变化，处理该行及必要的汇总。回调改值可能再次触发联动，先比较新旧值并约束重入，避免循环和重复请求。
5. **后续删除**：在删除完成后重新读取现存行并刷新汇总/显示，不再读取已删除行作为当前数据。
6. **保存/提交前**：只有业务确实需要阻断时才使用已确认的前置检查；本地显示成功不能替代后端必填、身份、数据权限和业务校验。

两份资料都允许多次注册事件。实施时应避免同一页面实例重复注册；重进页面是否为新实例、切换记录是否保留监听需实测，不能发明未查到的取消注册 API。

两份资料的“新增行复制最后一行”章节明确提示：`ready` 后手工添加才生效，默认新增空明细不适用。这也说明“页面初始化产生的行”和“之后点击新增的行”不能当作同一条已验证路径。

## 4. 前置检查与后置钩子不能互换

| 类型 | 资料合同 | 版本及限制 |
|---|---|---|
| `registerCheckEvent(type, fn)` | 指定操作执行前触发；回调获得 `callback`，调用才放行，不调用阻断后续操作 | 流程具体常量逐项核对；建模所读章节标注最低 `KB900190800` |
| `registerAction(actionname, fn)` | 指定动作完成后触发；按注册顺序执行 | 流程 `ACTION_ADDROW`/`ACTION_DELROW` 标注最低 `KB900190407`；建模对应章节标注最低 `KB900190800` |

两套对象的明细增删事件均需拼接明细表序号，例如目标是明细一时，在对应对象的常量后拼接 `"1"`。这个序号是明细表序号，不是行标识。

异步检查须明确通过、拒绝、异常和超时的处理与提示，不能在发请求后立即放行，又在异步完成时再次放行。后置钩子不能撤销已经完成的删除，也不能取代服务端授权。

原文示例同时出现历史 DOM 写值和推荐 API 写值，不能据此混用。字段状态和数据操作优先采用当前页面已确认的表单 API；DOM 可见性、CSS 隐藏不构成安全权限。

## 5. 最小现场验收

至少覆盖：空明细、首屏已有多行、删除后不连续行标识、手工新增、批量新增、修改依赖字段、删除末行、保存后重开、重复进入页面、非目标页面。涉及分页或移动端时，单独验证分页未显示行和移动端路径，不以 PC 通过替代。

验收同时看界面与保存后的实际数据；记录入口、版本、触发次数及错误证据。当前本卡仅完成静态来源核对，上述场景均未在客户环境执行。
